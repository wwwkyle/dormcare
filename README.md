# DormCare · 宿舍智能报修与反馈系统

**Smart Dorm Repair & Feedback System** — 学生报修 + AI 受理 + 确定性排班 + RAG 派活

中英双语 · 纯 Python 标准库 · 无需 pip install

---

## Quick start / 快速开始

```bash
cd dormcare
python app.py                                    # http://localhost:3000
python app.py --api-key sk-or-v1-xxxxxxxx        # 或直接传入密钥
export OPENROUTER_API_KEY=sk-or-v1-xxxxxxxx      # 或用环境变量
```

**先登录。** 只有一个入口，所有人从登录页进去；进去之后是**哪个界面，由账号的角色决定，
不是由地址决定**：

<http://localhost:3000/login.html>（或者直接访问 <http://localhost:3000/>，会被引导过去）

登录页上「登录」与「学生注册」是**两个并列的独立面板**，同时可见，不再互相遮挡：
第一次来的人不需要先点一下才能看到注册入口。

### 发布为公网网站

项目已提供 `Dockerfile`，可部署到任意支持 Docker 与持久化磁盘的平台：

```bash
docker build -t dormcare .
docker run -p 3000:3000 -v dormcare-data:/data \
  -e DORMCARE_PUBLIC_ORIGINS=https://你的域名 \
  -e DORMCARE_TRUST_PROXY=1 \
  -e DORMCARE_COOKIE_SECURE=1 \
  dormcare
```

部署平台还需配置：

- `DORMCARE_PUBLIC_ORIGINS`：用户实际访问的网站来源（含 `https://`）；多个域名用逗号分隔。
- `DORMCARE_TRUST_PROXY=1`：平台通过反向代理转发时启用，使服务端识别公网 Host/HTTPS。
- `DORMCARE_COOKIE_SECURE=1`：公网 HTTPS 部署必须启用，确保登录 Cookie 只经 HTTPS 发送。
- 将持久化磁盘挂载到 `/data`，否则平台重启后新注册账号和工单可能丢失。
- 可选配置 `OPENROUTER_API_KEY`；不配置时登录、报修和排班仍可使用规则降级模式。

不要把 `DORMCARE_PUBLIC_ORIGINS` 配成 `*`。服务端仍会拒绝未配置的跨站来源，
只是不再把经过受信反向代理的真实用户误判为「请求来源不被信任」。

**登录后先落在主菜单 `/menu.html`。** 三种角色进的是同一个页面，菜单里只列出
这个角色能打开的功能；点卡片进入**一个只做这一件事的详情页**，每个详情页右上角
都有「☰ 主菜单」可以随时回来。

| 角色 | 账号 | 密码 | 住在哪 | 菜单里能点开的 → 打开的页面 |
| --- | --- | --- | --- | --- |
| 🎓 学生 | `2024001` | `dorm2026` | 逸夫书院 · 东座 1 栋 · A-301 | 我要报修 → `/report.html`<br>我的报修记录 → `/records.html`<br>账号设置 → `/account.html` |
| 🎓 学生 | `2024002` | `dorm2026` | 学勤书院 · A 座 · F-303 | 同上 |
| 🎓 学生 | `2024003` … `2024010` | `dorm2026` | 每个账号一间房，见 `app.SEED_USERS` | 同上 |
| 🛠️ 师傅 | `A01` · `B02` · `C03` | `fix2026` | — | 排班与派活 → `/plan.html`<br>我的工单 → `/jobs.html`<br>账号设置 → `/account.html` |
| 🧭 管理员 | `admin` | `admin2026` | — | 运行总览 → `/overview.html`<br>全部工单 → `/tickets.html`<br>账号管理 → `/users.html`<br>维修班组 → `/roster.html`<br>账号设置 → `/account.html` |

**一张卡片 = 一个页面 = 一件事。** 以前三种角色各是一个长页面，学生端把报修表单、
报修记录、账号设置堆在一起。现在 11 个页面各管一件事，页面上**不会出现别的区块**——
`dom_smoke.js` 对每个页面都断言「不携带其他区块的控件」，防止它悄悄长回去。

这**不放宽任何权限**：每个页面仍然只属于一个角色（`/account.html` 除外，见下），
从地址栏输别人的页面照样 `303` 回菜单，菜单里的卡片只是链接。

学生也可以用学号自助注册（登录页右侧面板，需要填书院 + 楼栋 + 宿舍号）。
师傅与管理员账号都不开放注册：一个能读到别人房间号和电话的账号应当是**发放**的，
不该是自取，也不该是自己能注册的。

若未配置密钥，页面底部会出现「启用模型密钥」输入框（需登录后可见），
粘贴 OpenRouter 密钥即可（密钥只存在服务端进程内存中，不落盘、不进前端）。

> 演示数据是**一个账号一间房**。之前 10 张工单全挂在 `2024001` 名下、横跨 9 个书院，
> 那是因为地址字段不跟账号校验；现在地址是账号的属性，演示数据也必须拆成
> 10 个住在不同房间的学生（见 `serve.py`）。
>
> 其中第 11 张单是**故意排不进去**的（40 分钟的电路维修，学生只留了 30 分钟），
> 用来演示「排不进当天」这条闭环 —— 师傅端会出现处理面板，学生端会收到提示。

## 自己就能改的两件事 / The two things you can change yourself

搬宿舍了、或者只是想把密码换掉，都不必等物业。这两个接口**只作用于当前会话**，
请求体里根本没有「账号 id」这个字段 —— 所以它们在结构上就不可能改到别人头上，
也正因为如此才敢对所有角色开放（师傅和管理员同样能在自己的控制台里改自己的密码）。

| | 改宿舍 | 改密码 |
| --- | --- | --- |
| 入口 | 学生端「账号设置」卡片（主菜单 → 账号设置） | 同左 |
| 接口 | `POST /api/account/room` | `POST /api/account/password` |
| 谁能用 | **只有学生**（师傅与管理员没有宿舍，返回 `403`） | 三种角色都能改自己的 |
| 校验 | 书院必须存在；**有真实楼栋清单的书院必须选楼栋**；宿舍号必填、截断到 30 字符 —— 与注册、后台更正完全同一套规则 | 必须给出**当前密码**；新密码过强度校验；不允许与旧密码相同 |
| 生效 | **向后生效**：之后提交的工单落在新地址 | 立刻生效，且**吊销该账号的其它所有会话** |
| 不影响 | **已提交工单的地址不改写** —— 一张故障记录记的是「故障当时在哪」，改写它会把已经在路上的师傅派到错门口 | **当前这一个会话保留**：正在改密码的这个标签页不会被自己踢出去 |

管理员后台的「更正宿舍 / 重置密码」依然保留，作用不变：处理**别人**的账号，
以及别人自己改不了的情况（例如已经搬走联系不上的学生）。两者是同一件工具的两个入口。

## 学生端看到什么 / What the student console shows

学生端只回答一个问题：**我的报修现在怎么样了**。系统内部的排班常数不属于这个答案。

| 不显示 | 为什么 |
| --- | --- |
| 「排班规则（系统固定值）」卡片 | 那是引擎的输入，不是给住户看的产品说明（**学生端与师傅端都已移除**这一整块） |
| 损坏类型 chip 上的分钟数 | 同上；而且会引来「你说 60 分钟为什么修了 80 分钟」的争论 |
| 「预计维修时长（固定）」「同书院单次路程」 | 同上 |
| AI 结果卡里的「固定工时」 | 同上 |
| 报修记录行里的时长徽章 | 同上 |

做法不只是「前端不画」：`/api/intake/parse` **不再返回** `duration_minutes`，
`ai_agents._context_line()` 也**不再把工时告诉模型** —— 不递给模型一个数字，
是让它不去引用这个数字最可靠的办法。提示词里同时明令禁止出现任何分钟数。
`edge_cases.py` 会扫描学生能读到的每一段文本，出现 `\d+ 分钟` 直接判失败。

学生端仍然会看到**负责人、上门时段、排队状态、空闲时间、紧急度**，以及：

- **AI 追问**：描述太笼统时，AI 不给结论，而是问出缺的那几点（具体位置、什么时候开始、
  现在还能不能用），旁边一个按钮把这些问句直接填进故障描述框，答完再提交。
- **自检建议**：描述够清楚时，AI 给 1-3 条**上门前自己就能安全做完**的操作
  （例：「把滤网取下用清水冲洗、晾干后装回」）。涉及 220V 电路、燃气、拆解设备、
  登高的动作一律不写，改为「不要自行处理，等待师傅」。

> 无模型时同样成立：`ai_agents.SELF_HELP` 是 17 个类别 × 中英双语 × 2 步的确定性兜底表，
> `_fallback_extras()` 按描述长度决定是追问还是直接给建议。

## 排不进当天怎么办 / When a job will not fit into the day

排班引擎是确定性的，不会为了讨好谁而弯曲：学生声明的时间窗装不下这一单，它就排不进去，
点多少次「生成排班」都一样。但引擎不站在楼里 —— **只有师傅能决定**是顺路去做，
还是让这个学生改约。于是师傅端多了一个面板：

| 师傅看到 | 说明 |
| --- | --- |
| 工单号、书院 / 楼栋 / 房间、公共区域标记 | 不用先去别处查 |
| 维修类别、固定工时、紧急度、需要备件 | 判断值不值得顺路 |
| **排不进去的原因** | 班次满了 / 落在空闲时段外 / 空闲时段比工时还短 / 学生没填空闲时间 |
| 学生声明的时间窗、姓名、电话、故障描述 | 决定前不用先打电话问 |

两个按钮，两条完全不同的路径：

- **顺路去修** → 状态变 `accepted`，工单打上 `off_route: true`。它**不会**被塞进当日时间轴
  —— 引擎没排它，画上去时间轴就是假的。学生端看到「李师傅会顺路过去处理」。
- **建议改约** → 选一个新日期（可选留言），工单打上 `reschedule_requested: true`。
  学生端出现一段确认区：**接受新时间** 或 **暂不接受**。
  接受则沿用原来登记的时段、把工单挪到新日期重新进入排班；不接受则清除建议、日期不变。

服务端两道校验：只有**这一单所属的那位师傅**能操作，而且这一单必须**真的排不进去**
（否则 `409 on_route`）—— 不然「未排入」面板就成了给已排好的单贴标签的地方。

## 管理员端 / The administrator console

第三个角色，做的是另外一件完全不同的事：管理员**既不报修也不修**，所以它名下没有工单、
也没有路线。它能做的是**看清全局**和**维护账号**。

| 页面板块 | 内容 |
| --- | --- |
| 运行总览 | 工单总数 / 学生账号 / 师傅账号 / 班组人数 / 今日工单 / 今日待办 / 平均评分 |
| 分布 | 按状态、按紧急度、按书院三组计数（书院名按界面语言本地化） |
| 全部工单 | 系统内**每一条**报修单，带**报修人账号**、联系方式、负责师傅、上门时间、状态与排队状态；可删除任意一张 |
| 账号管理 | 每个账号（角色徽章 + 姓名 + 账号 + 报修地点 + 持单数）。可**更正宿舍**、可**重置密码** |
| 新建账号 | 学生（学号 + 姓名 + 书院 + 楼栋 + 宿舍号）或**发放师傅账号**（工号 + 工种 + 可承接类别 + 是否持证 + 分机） |
| 维修班组 | 每位师傅的工种、可承接类别、是否持证、内部分机 |

三个动作值得单独说，因为它们正是**别的角色做不了**的事：

1. **更正宿舍** —— 宿舍号是每张工单的报修地址，而学生**不能**自己改（地址一旦可自选，
   「我的记录横跨 9 个书院」就会回来）。登记错了只能由这里改，改完学生端立刻生效，
   **之后提交的工单就落在新地址**。
2. **重置密码** —— 同时**吊销该账号全部会话**。「改了密码但旧会话还活着」不算改密码。
3. **发放师傅账号** —— 必须**同时**建两半：师傅档案（`assign_day()` 按它派活）和绑定它的
   账号（师傅端按它解析「我的今天」）。只建一半，要么是个登不进任何活的账号，
   要么是个没人能登录的档案。所以工单里**必须**至少勾一个可承接类别 —— 否则引擎永远
   不会把活派给他。

它的数据接口是独立的一组 `/api/admin/*`，而不是复用学生的或师傅的 —— 因为服务端递给
那两个角色的都是**切片**，而「切片」恰恰是管理员不该拿到的。反过来也一样：
`/api/tickets`、`/api/plan`、`/api/intake/parse`、`/api/schedule/optimize` 对管理员一律 `403`。

## 报修地点 = 账号的宿舍 / The address belongs to the account

这是这套系统里最容易被忽略、也最要紧的一条约束。

| | 以前 | 现在 |
| --- | --- | --- |
| 地址从哪来 | 每次报修手填 `college` / `block` / `dorm` | **账号上的宿舍**，注册时确定 |
| 服务端校验 | 只跟全局书院 / 楼栋表比对 | **跟会话账号比对**，请求体里的地址一律忽略 |
| 后果 | 一个账号可以「住」遍全校 9 个书院 | 每条记录都落在自己的房间 |
| 例外 | 无 | 勾选「公共区域报修」后解锁手填，工单标记 `public: true` |

- 服务端在 `_api_create_ticket` 里从会话取地址：`college = user["college"]`、
  `block = user["block"]`、`dorm = user["dorm"]`，请求体里同名字段直接丢弃。
- 唯一合法的例外是**公共区域**（走廊灯、洗衣房、公共卫生间）：前端勾选后提交
  `public_area: true`，此时才允许指定另一个地址，且必须指定；工单会被打上
  `public` 标记，在学生端显示「公共区域」徽章。
- 账号缺宿舍时（历史数据）报错 `account_no_address`，而不是静默接受一个空地址。

## 身份与权限 / Identity & authorisation

系统里有三种角色，权限从浏览器搬到了服务端：

| | 学生 | 师傅 | 管理员 |
| --- | --- | --- | --- |
| 看得到的工单 | **只有自己提交的** | **只有引擎派给自己的** | 全部（带报修人账号） |
| 能做的动作 | 报修、撤单、**验收 / 评价 / 打回** | **接单、完工** | 更正宿舍、重置密码、发放账号、删除工单 |
| 能用的 AI | 受理分类、报修建议 | 逐单派活说明、排班依据 | ❌（不报修、不派活） |
| 排班 | ❌ | 只排**自己**当天（`worker` 参数会被服务端忽略） | ❌ |
| 落在哪 | `/menu.html` | `/menu.html` | `/menu.html` |
| 有几个页面 | 3（报修 / 记录 / 账号设置） | 2（排班 / 工单）+ 账号设置 | 4（总览 / 工单 / 账号 / 班组）+ 账号设置 |
| 改自己的宿舍 | ✅ `/account.html` | ❌（没有宿舍，该区块被移除） | ❌（不是住户，同上） |
| 改自己的密码 | ✅ `/account.html` | ✅ `/account.html` | ✅ `/account.html` |

几个刻意的设计：

- **工单归属由会话盖章**（`ticket["user_id"]` 取自 session，不取请求体），
  所以「只能看自己的」这句话是可以被强制执行的。
- **师傅的活由引擎分配**，不由师傅自己抢：`scheduler.assign_day()` 按
  *工种匹配 → 持证要求 → 负载最轻* 逐单派发，纯算术、可复现。
  空调 / 强电 / 家电这类标了 `certified` 的活只会给持证师傅。
- **师傅与管理员账号都不开放自助注册**：一个能读到别人房间号和电话的账号应当是「发放」的，
  不该是「自取」的。管理员账号由 `SEED_USERS` 预置，师傅账号由管理员在管理台发放。
- **管理员不是超级用户**：它拿到的是「全局只读 + 账号写入」，而不是「能用任何人的身份」。
  三组控制台互相 `403` / 重定向，方向是双向的（见 `test_admin.py`）。
- **写操作校验归属**：`/api/tickets/status`、`/api/tickets/delete`、
  `/api/tickets/feedback` 都会先确认这张单确实属于调用者，再动手（防 IDOR）。
- **会话是服务端可撤销的不透明令牌**：HttpOnly + SameSite=Lax Cookie，
  退出登录即失效；账号是 PBKDF2-SHA256（每个用户独立盐，20 万轮）。

## 需求对照 / Requirement mapping

| 需求 | 实现位置 |
| --- | --- |
| 学生端：上传损坏类型（桌子、椅子、空调…） | `config.REPAIR_TYPES` — **17 类**，中英双语，每类固定工时 |
| 学生端：上传空闲时间 | 30 分钟一格的时段网格，学生自由勾选/拖动；可多段 |
| 学生端：哪个书院 + 楼栋 + 宿舍号 | 注册时填一次（书院下拉 **8 个** + 楼栋/座按书院过滤 + 宿舍号），之后**由账号带出、只读**；公共区域报修才解锁手填 |
| 学生端接 AI，可直接接入 RAG 工单 | `ai_agents.parse_intake()` — 知识库注入 → 模型分类/追问/自检建议 → 落成结构化工单 |
| **AI 针对故障适当追问，或给可行易操作的建议** | `INTAKE_SYSTEM` 的 `need_more_info` / `follow_up` / `self_help` 三个字段；无模型时由 `SELF_HELP`（17 类 × 双语 × 2 步）+ `_fallback_extras()` 兜底。学生端把追问做成「一键填进描述框」 |
| 工人端接 AI，按当天日期 + 学生上传内容排班 | `scheduler.assign_day()`（派给谁）+ `scheduler.schedule_day()`（几点到几点） |
| 接 AI 做 RAG，给师傅排活 | `ai_agents.advise_dispatch()` — 逐单作业指引 + 备件 + 搬迁提醒 |
| **不同类型预计维修时间不一样，要固定** | `config.REPAIR_TYPES[*].minutes` — 查表，不估算、不压缩（**师傅端可见，学生端不可见**） |
| **书院之间往返 15 分钟** | `TRAVEL_RULES["cross_college_minutes"] = 15` |
| **书院内 5 分钟** | `TRAVEL_RULES["same_college_minutes"] = 5` |

## 架构 / Architecture

```
Browser ──POST /api/...──▶ app.py ──HTTPS──▶ OpenRouter /chat/completions
                             │
                             ├── config.py     固定知识库（工时 / 书院 / 路程 / RAG 语料）
                             ├── scheduler.py  确定性排班引擎（纯算术，零模型参与）
                             ├── ai_agents.py  4 个 RAG 智能体（分类 / 建议 / 派活 / 解释）
                             └── store.py      JSON 存储（data/store.json）
```

前端是**一个主菜单 + 九个详情页**。每个详情页恰好加载 `common.js` 加**它自己那一个**
模块 —— 页面与脚本一一对应，互不引用：

```
common.js          全部页面共享：i18n 全量表 · Markdown · 请求封装 · 会话身份 · 日期/时段工具
                   · 健康检查 · 密钥面板 ·「☰ 主菜单」按钮
                   · 跨页复用的纯函数（priLabel / pairsText / stars / row / collegeOptionsHtml …）
login.js           登录 / 学生注册（两个并列面板；跳转目标由服务端返回）
menu.js            主菜单 · 按角色渲染入口卡片（唯一知道三个角色各有哪些页面的模块）

student-report.js  我要报修：AI 受理 · 损坏类型 · 空闲时段网格 · 提交
student-records.js 我的报修记录：状态 · 上门时间 · 改约回应 · 评分反馈
account.js         账号设置：更正宿舍（仅学生看得见该区块）+ 修改密码（三角色通用）
worker-plan.js     排班与派活：当日路线 · 统计卡 · 时间轴 · 未排入工单处理 · AI 派活
worker-jobs.js     我的工单：接单 / 完工 · 学生评分回显
admin-overview.js  运行总览：统计卡 · 按状态/紧急度/书院的分布
admin-tickets.js   全部工单：带报修人 · 状态筛选 · 删单
admin-users.js     账号管理：更正宿舍 · 重置密码 · 发放学生/师傅账号
admin-roster.js    维修班组：师傅名册 · 工种 · 持证 · 可承接类别（只读）
```

拆分时真正跨页复用的只有**纯函数**：`priLabel` / `pairsText` / `stars` / `row` /
`collegeOptionsHtml` / `blockOptionsHtml` 之类提到 `common.js`，而不是把「查优先级名字」
抄进九个文件里任其漂移。状态与事件处理**不共享** —— 那正是每个页面只做一件事的原因。

两个刻意的结构后果：

- 管理端四个页面**一个都不加载** `student-*.js` 或 `worker-*.js`，所以
  「管理员不是超级用户」在代码结构上也成立，而不只是靠服务端拦。
- 菜单里的卡片只是链接。服务端仍然对每个页面独立放行，所以菜单里没有的入口，
  直接在地址栏输 URL 一样进不去。

### 核心设计原则：**引擎决策，模型说明**

> The ENGINE decides. The MODEL explains.

排班表里的每一分钟都由 `scheduler.py` 用 `config.py` 里的固定值算出。
**连「这单该派给谁」也是算术**：`assign_day()` 按工种匹配 → 持证要求 → 负载最轻
逐单派发。语言模型只做两件事：**分类**（把故障描述映射到类别）和**写字**（把结果讲清楚）。
它**从不产生任何数字**。因此同样的工单永远得到同样的排班与同样的派单，
结果可解释、可复现、可答辩。

## 排班算法 / Scheduling engine

### 第一步：派给谁 / Step 1 — whose job is it

`assign_day(day, tickets, workers)` 把当天每一张待办工单指派给**唯一一位**师傅：

| 顺序 | 规则 |
| --- | --- |
| 1 | 师傅的工种清单（`specialties`）必须覆盖该报修类别 |
| 2 | 标了 `certified` 的类别（空调 / 强电 / 家电）只给持证师傅 |
| 3 | 都符合时，给当前负载最轻的那位；并列则按种子顺序 |

先按 `(优先级, 报修时间, 单号)` 排好队再派，所以顺序与结果都是确定的。
这个函数存在的理由很直接：**师傅登录后只能看到自己的活**，
那就必须有人先决定这活是谁的 —— 而这件事不能交给模型。

### 第二步：几点到几点 / Step 2 — the day itself

`schedule_day(day, tickets, worker)` — **两遍贪心**，规则全部硬约束：

| 约束 | 规则 |
| --- | --- |
| 工时 | 每单占用其类别的**固定**时长，不估算、不压缩 |
| 路程 | 相邻两单同书院 **5 分钟**；跨书院 **15 分钟** |
| 首单 | 从维修间出发，按跨书院 **15 分钟**计 |
| 班次 | `08:30 – 18:00` |
| 午休 | `12:00 – 13:30`，任何作业**不得跨越** |
| 空闲时间 | 每单必须**完整落在**学生声明的某一空闲时段内 |
| 排序 | 紧急(3) > 较急(2) > 一般(1) > 不急(0)；同级按报修时间先到先做 |

两条硬约束（空闲时间、午休）**优先于**优先级：优先级只决定排队顺序，
不会让系统把作业塞进学生没空的时间。

### 为什么要两遍 / Why two passes

**Pass 1** 按优先级顺序把工单**追加**到当天路线末尾 —— 这是正确的排序规则。
但"只追加"会漏掉一类可排的工单：如果某单声明的空闲时段**早于**当前游标，
它会被跳过；而**当天剩余时间其实还够**，直接判为「排不下」并不诚实。

**Pass 2** 因此重新审视每一张被跳过的工单，把它插进**第一个真正放得下的空档**，
并选择**搬迁成本最低**的插入位置（用 `_travel_insert_cost` 比较）。
优先级顺序不会被破坏 —— Pass 2 只填 Pass 1 没用掉的空间，**永远不会挤掉已排的工单**。

实测：9 张工单的负载下，Pass 1 排出 5 单，Pass 2 又救回 1 单（校门门锁），
最终 6 单，且 0 条规则违反、结果仍然确定性。
剩余 3 单经逐条核验是**真的排不进** —— 学生声明的空闲时段本身已经关闭。

排不下时系统会区分三种原因，而不是笼统报「排不下」：

| 原因码 | 含义 |
| --- | --- |
| `no_time_left` | 班次排满，或剩余时间无法再接一单 → 建议改约次日 / 增派师傅 |
| `window_too_short` | 学生声明的空闲时段**短于**该类维修的固定工时 → 需请学生放宽时间 |
| `no_availability` | 学生未登记任何空闲时间 → 需先联系学生补充 |

### 一个真实的排班轨迹

```
shift 08:30 at workshop
  + 15 cross-college  -> earliest 08:45
  stop 1  TD485D8AD  Air conditioner  (urgent)
          pushed to window 09:00 (+15 min wait)   fixed 60 min  -> 09:00-10:00
  + 15 cross-college  -> earliest 10:15
  stop 2  T24A2FEC6  Chair  (high)                 fixed 25 min  -> 10:15-10:40
  + 15 cross-college  -> earliest 10:55
  stop 3  TBF1ACEFC  Bed frame  (normal)
          would run 10:55-11:45, inside the free window, so it flies…
          (in the 6-ticket scenario this is where lunch forces 13:30)
```

## 工单的一生 / The life of a ticket

```
学生提交 ──▶ pending ──[师傅接单]──▶ accepted ──[师傅完工]──▶ done ──[学生验收]──▶ confirmed
                ▲                        ▲                      │
                │                        └──────────────────────┤
                └────────[学生打回 / 1-2 星差评自动回退]───────────┘
```

| 状态 | 中文 | 谁能改 | 学生端看到什么 |
| --- | --- | --- | --- |
| `pending` | 待受理 | 学生可撤回 | 已排定「{师傅} 将于 {日期} {时间} 上门」（若能排进） |
| `accepted` | 已接单 | 师傅 | 谁来了，几点到 |
| `done` | 已完工 | 师傅 | 出现 5 星评分 + 留言框，可「确认完成」或「还没修好」 |
| `confirmed` | 已验收 | 学生 | 结案，保留评分与留言 |

**这是原来那版最缺的一块。** 之前工单只有 `pending / done` 两态，
系统叫「报修与反馈」却没有任何反馈：学生不知道谁来做、几点来，也说不出一句评价。
现在「谁来做」来自 `assign_day()` + `schedule_day()` 算出的上门时间，
「做得怎么样」由学生落成 1-5 星 + 一句话，并且**差评会把工单退回队列**——
反馈真的会改变系统的状态，而不只是存一个数字。

## 四个 RAG 智能体 / The four agents

| 智能体 | 端 | 输入 → 输出 | 是否允许产生数字 |
| --- | --- | --- | --- |
| 受理分类 | 学生 | 故障描述 → 类别 ID / 紧急度 / 置信度 | ❌ 时长由系统查表 |
| 学生建议 | 学生 | 故障 + 上下文 → 安全提示 + 报修指引 | ❌ 只引用固定工时 |
| 维修调度 | 师傅 | 权威排班表 → 逐单作业指引 + 备件 + 搬迁建议 | ❌ 不得改动任何时间 |
| 排班解释 | 师傅 | 权威排班表 → 4 句以内解释排班依据 | ❌ 不得改动任何时间 |

RAG 语料 = `config.py` 中的三张表（报修类型 + 书院 + 路程规则），
在每次请求时渲染成 Markdown 注入 system prompt，并在提示词中明确声明为
**唯一信息来源**，禁止使用外部知识。

### 降级设计 / Graceful degradation

模型不可用时（未配置密钥、网络故障、限流）系统**不会瘫痪**：

- 分类 → `fallback_classify()` 关键词规则兜底（中英双语词表）
- 学生建议 / 派活 → 由固定规则生成完整答复（不是错误页）
- 排班 → **完全不受影响**，因为排班从来不依赖模型

> 模型挂了，报修照样能提交，排班照样能出。

## 双语的实现 / How bilingual works

| 层 | 做法 |
| --- | --- |
| 前端文案 | `common.js` 的 `I18N` 表（中英各约 180 条），`data-i18n` 属性驱动；两个页面共用同一份 |
| 切换语言 | 写 `localStorage`，`DC.afterLang()` 注册的角色重绘钩子同时刷新 |
| 服务端错误 | 返回稳定的 `code`（如 `bad_college`），前端按 code 本地化 |
| AI 提示词 | **按语言分两套完整提示词**，而非在一段提示词里要求「请说英文」 |
| AI 固定回复 | `MSG_OUT_OF_SCOPE` / `MSG_NOT_IN_KB` 各有中英两版，逐字照抄 |
| 语言透传 | 页面把 `lang` 随请求发送，`GET /api/tickets`、`/api/plan` 也接受 `?lang=`，保证服务端解析出的标签与界面语言一致 |

> 为什么提示词要分两套：把「请用英文」这条指令埋在一大段中文提示词里，
> 模型经常无视；而提示词本身就是目标语言时，模型会稳定遵守。
> 这一点在测试中被实测确认（见 `edge_cases.py`）。

## 安全 / Security

- **账号**：密码以 PBKDF2-SHA256 存储（每个用户独立盐、20 万轮），比较用 `hmac.compare_digest` 常量时间；登录失败时即使账号不存在也照跑一次哈希，接口无法用来枚举学号
- **会话**：不透明随机令牌（非签名 payload），服务端持有映射 → 退出登录**立即**吊销；Cookie 为 `HttpOnly; SameSite=Lax`
- **授权在服务端**：每个接口先看会话再碰数据；工单归属由会话盖章，页面与脚本各自声明所需角色，未获授权时**重定向**而非隐藏
- **管理员不是超级用户**：管理员的读写集中在独立的一组 `/api/admin/*`；`/api/tickets`、`/api/plan`、排班、派活、报修、接单对它一律 `403`，它读到的每一行都是「全局只读 + 账号写入」，不能借用任何人的身份动作
- **口令重置即吊销会话**：`/api/admin/user/password` 改完摘要会顺手删掉该账号的全部会话 —— 改了密码但旧 Cookie 还能用，等于没改
- **防 IDOR**：改状态 / 删单 / 评价都先确认该单属于调用者（学生看 `user_id`，师傅看派单结果）
- **防冒充**：请求体里的 `worker` 参数一律忽略 —— 会话说了算
- **地址不取请求体**：`college` / `block` / `dorm` 由会话账号写入，否则一个学生可以替任意宿舍报修（这正是"我的记录横跨 9 个书院"的成因）。唯一出口是显式的 `public_area: true`
- **登录限流**：按 `(来源, 账号)` 计失败次数（10 次 / 5 分钟），只有**失败**才计数，所以一个同学打错密码不会连累同一 NAT 下的其他人
- **跨站**：POST 校验 `Origin` 与 `Host` 一致；`application/json` 本身也不可由跨站表单发出，SameSite=Lax 是第三道锁
- 密钥只存在于**进程内存或环境变量**，绝不写入本目录（本目录发布后所有文件可被公开下载）
- 密钥不写日志、不回显、不发送到浏览器；`/api/setup` 需登录
- 静态文件走**显式白名单**（`STATIC_FILES`，每个条目带所需角色），并拒绝点开头文件 → 无路径穿越
- 按客户端 IP 限流（120 次 / 60 秒）；`.env` 类文件不在白名单内，无法被读取
- 学生只能看到**自己**的工单、姓名与联系方式；师傅的分机号只发给师傅角色

> 一句话：**「看不到」不是前端把按钮藏起来，而是服务端不给数据。**
> 权限边界由 `test_auth.py` 用 74 项攻击式断言逐条盯着（见下）。
> 引入主菜单之后，「菜单不是绕过权限的后门」由 `test_account.py` 单独盯着：
> 三个角色各自能打开菜单，但任何角色从地址栏进别人的控制台仍然被重定向。

`smoke_test.py` 会对排班结果逐条校验不变量：固定工时是否与查表一致、
路程是否为 5/15、是否跨越午休、是否落在学生声明的空闲时段内、
优先级顺序是否单调、以及**同样输入是否得到完全相同的排班（确定性）**；
另外验证工单生命周期两半（师傅接单 → 完工 → 由**提交人**评价 → 别人评价被拒）、
`/api/workers` 对学生的响应里**没有分机号**，以及 25 条页面/脚本的角色放行矩阵（含主菜单）；
AI 受理必须**要么带回自检建议、要么带回追问**，且响应里**不得出现 `duration_minutes`**。

`edge_cases.py` 的 PART C 专门盯「排不进当天」这条闭环，用的是真正排不进去的单
（50 分钟的床架维修，学生只留了一个 30 分钟时段）：
匿名 / 学生 / 非本人师傅一律拒绝 → 师傅**顺路去修**后工单**仍然不在**优化时间轴上
（引擎没排它，画上去就是假的）但学生端能看到「会顺路处理」→ 另一单走**建议改约**，
跨账号抢答 `403` → 学生接受后日期真的变了并重新进入排班 → 重复回应 `409 no_suggestion`
→ 学生拒绝则建议清除、日期不变 → 已排进路线的单不能被宣布为「未排入」(`409 on_route`)。
另外它会扫过全部 17 个类别的自检建议，**任何把学生往 220V 电路、燃气、拆解设备或
登高上引**的步骤都会让测试失败。

带着**真实的会话 Cookie** 打到运行中的服务上，覆盖 435 项前端行为：

匿名 `303` 去登录）、**6 个已删除的合并页面一律 `404`**、
**登录页上 tab 已消失且登录 / 注册两个面板同时可见**、

## 多模态、完工凭证与对话受理（新增）

学生报修页支持相机/相册多图（最多 5 张；每张解码后不超过 5MB；仅 JPEG/PNG）、
预览删除和 Web Speech API 语音转写。语音结果只填入可继续编辑的描述框；浏览器不支持、
用户拒权或识别失败时会显示降级提示，手工报修始终可用。Web Speech API 是否免费及是否
把音频发送到浏览器厂商服务由浏览器实现决定，本项目不收取费用，也不保证所有浏览器可用。

师傅将工单从 `accepted` 标记为 `done` 时必须提交至少一张完工图。学生记录页可查看
报修图、完工图、完成时间、完工师傅，并确认或评价。持久化状态仍使用兼容值
`pending / accepted / done / confirmed`；API 另返回 `status_stage` 和
`status_stage_label`，对应“待受理 → 已派单/维修中 → 已完成待确认 → 关闭”。

### 新增 API 精确契约

- `POST /api/uploads`（学生/师傅）：JSON
  `{"purpose":"ticket|agent|completion","draft_id":"","images":[{"mime":"image/png|image/jpeg","data":"base64"}]}`。
  返回 `{"ok":true,"uploads":[{"id","mime","size","url"}],"limits":{...}}`。
  学生不能上传 `completion`，师傅只能上传 `completion`。
- `GET /api/uploads/<id>`（登录）：返回图片字节。仅图片所有者、工单学生、被派师傅或管理员可读；
  上传目录没有公开静态映射。
- `POST /api/agent/session`（学生）：`{"lang":"zh|en"}`，返回服务端会话。
- `POST /api/agent/message`（学生）：`{"id","text","image_ids":[],"transcript":false}`，
  返回 `reply/source/ready/draft/safety_warning`。会话保留最多 30 条历史。
- `GET /api/agent/session?id=<id>`（学生）：返回自己的会话、历史、草稿和创建结果；跨账号 `403`。
- `POST /api/agent/confirm`（学生）：`{"id","date":"YYYY-MM-DD","slots":[[start,end]],"contact":""}`。
  只有 `ready=true` 的未确认草稿可创建一次工单。
- `POST /api/tickets` 新增可选字段：`title`、`image_ids`（最多 5 个本人未绑定上传）。
- `POST /api/tickets/status`：`status=done` 时新增必填
  `completion_image_ids`（1-5 个当前师傅上传的完工图），否则
  `400 completion_images_required`。

Agent 草稿字段为 `title / repair_type / description / location / priority /
image_ids / expected_date`。高风险关键词（漏电、燃气、冒烟/起火、大面积漏水等）由
服务端规则强制提升为 `urgent` 并返回立即联系校园保卫/应急电话的提示。模型超时、网络错误、
无效 JSON 会重试一次，之后使用确定性规则追问/成稿；不会阻塞手工报修。

### 数据字段与兼容策略

JSON Store 新增 `uploads`、`agent_sessions` 集合；工单新增惰性可选字段
`title`、`image_ids`、`completion_image_ids`、`completed_at`、`completed_by`、
`agent_session_id`。**无迁移脚本，惰性默认字段兼容**：旧 JSON 加载时自动补空集合，
旧工单读取时将缺失字段视为空列表/空值，旧状态值不改写。

上传实体记录 `id / owner_user_id / purpose / draft_id / ticket_id / mime / size /
filename / created_at`。文件名由服务端随机生成，读取只使用记录内 basename；服务端校验
base64 解码后大小和 PNG/JPEG magic bytes，客户端 MIME 声明不能绕过检查。

### 环境变量

- `DORMCARE_DATA`：JSON Store 路径，默认 `data/store.json`。
- `DORMCARE_UPLOAD_DIR`：上传目录；默认与 `DORMCARE_DATA` 同目录下的 `uploads/`。
  Docker 默认因此为 `/data/uploads`，与 Store 一起落在持久卷。
- `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`：OpenAI 兼容接口。
  `OPENAI_BASE_URL` 应为包含 `/v1` 的基地址，服务端追加 `/chat/completions`。
- `OPENROUTER_API_KEY`、`OPENROUTER_MODEL`：继续兼容；OpenAI 变量优先。
  API Key 只在环境变量或进程内存中，绝不写入 Store。

## 可调参数 / Tunables

全部集中在 `config.py`，改完全局生效：

```python
TRAVEL_RULES = {
    "cross_college_minutes": 15,   # 书院之间往返
    "same_college_minutes": 5,     # 书院内
    "workday_start": "08:30",
    "workday_end": "18:00",
    "lunch_start": "12:00",
    "lunch_end": "13:30",
    "scheduling_days": 5,
}
```

修改任一报修类型的固定工时，只需改 `REPAIR_TYPES` 中该类的 `minutes` —
排班、前端显示、AI 提示词三处会同时生效。

师傅的**工种范围**同样在 `config.py` 的 `SEED_WORKERS[*].specialties` 里 ——
它决定 `assign_day()` 把哪一类活派给谁；标了 `"certified": True` 的师傅才能接
空调 / 强电 / 家电这三种标了 `certified` 的类别。演示账号在 `app.py` 的
`SEED_USERS`（口令分别是 `DEMO_STUDENT_PASSWORD` / `DEMO_WORKER_PASSWORD` /
`DEMO_ADMIN_PASSWORD`），会话有效期 `auth.SESSION_DAYS`（默认 7 天），
口令最低长度 `auth.MIN_PASSWORD`，登录失败预算 `app.AUTH_MAX_FAILURES`。

> 想改「有哪些角色」只改三处：`auth.py` 的角色常量与 `HOME_BY_ROLE`、
> `app.py` 的 `STATIC_FILES`（哪个页面属于谁）、`common.js` 的 `HOME` 与 `roleLabel`。
> 少改任何一处，页面级隔离就会出现一条缝。
